## The request (a learner, in the app's 💬 box, 2026-09-03)

> "Hi ma'am can ma'am make the quests so that they remember what question you did wrong
> and theres an option to do it again"

Two halves: (1) the app keeps a memory of what you got wrong, (2) you can go and do those
again. Today the app forgets a round the moment it ends. What exists is NOT this:
second chance on one wrong tap (half marks), Help mode after three failed quests (hints
open by themselves, second try on every question), and Play again (a whole fresh quest).

## Facts that shape the design (all checked on disk 2026-09-04)

- **Dealing is unseeded.** `js/ui.js` `randInt` / `pick` / `shuffled` use `Math.random`;
  `js/engine/interactive.js` too. There is no seed to store and replay.
- **A dealt question is NOT plain data.** Interactive items carry live functions
  (`build: (host, done) => pointDrop(...)` in q2, `onChange` handlers in q5, q6, qI, qT).
  They cannot be put in localStorage and rebuilt.
- **Every dealt item carries a `skillId`.** `buildRound()` in `js/quests/index.js` picks
  a skill `s` from `q.skills`, calls `s.gen()`, and stamps `built.skillId = s.id`. The
  per-item record `{ i, skillId, outcome, xp }` in `js/play.js` (`recordAnswer`) already
  reaches `onFinish` as `answered`. Exam mode (q7) uses `q.buildAll()` instead.
- **Storage today.** Standalone: `LocalBackend` in `js/backend.js`, one localStorage
  profile `{ name, xp, quests, met }`; `saveResult()` replaces `quests[questId]`
  wholesale, top-level fields survive (that is why `met` lives at the top). Blipwork:
  `HostBackend(host)`, state lives on the server (`mhq_funfun_state`), XP is recomputed
  server-side from `answered` by `mhq_submit_funfun`. Changing that needs a migration.
- **Shells.** Standalone: `js/screens.js` (`mapScreen`, `resultScreen(res, questTitle,
  onAgain, onMap, onLesson)`), `js/app.js`. Blipwork draws its own: `js/funfun-play.js`
  (the mount host, `onFinished` → `app.go("results", { funfun: true, … })`),
  `renderFunfunResults(app, host, params)` in blipwork `js/screens.js` (called from
  blipwork `js/app.js` case "results"), and `funfunStrip(app, ch)` in the same
  blipwork `js/screens.js` (the 📈 strip on the Functions chapter).
- **Mount contract.** `js/mount.js` exports `runQuest(questId, ctx)` and
  `mountFunFunctions(rootEl, host)`; `runQuest` builds a `finished` callback that calls
  the backend's `saveResult(...)` and THEN `ctx.onFinished(res)`, and hands it to
  `startQuest(questId, finished, ctx.onExit, opts)`. A redo needs a sibling
  `runRedo(entries, ctx)` whose `finished` skips `saveResult` entirely.

## The design (decided by the facts; her rulings below can still change it)

**Same skill, fresh numbers.** Because the exact question cannot be stored, "do it
again" means: a fresh question of the SAME skill, from the same quest, with new numbers
and a new graph. The basket still shows WHAT she got wrong (the prompt text of the
original, snapshotted at the time), so the "remember" half is honest. Pedagogically this
is the better half anyway: it tests whether she now understands, not whether she
remembers the number.

**The basket ("Probeer weer").** A short per-device list, newest first:

```
entry = {
  id:      "<questId>:<skillId>",   // one entry per skill; a repeat miss bumps it up
  questId, skillId, concept,
  prompt:  { en, af },              // the ORIGINAL question's prompt, plain B() object
  when:    "2026-09-04T10:12:00Z",
  misses:  1,                       // +1 every time the same skill goes wrong again
  outcome: "wrong" | "skipped"      // what happened the last time
}
```

- Stored in localStorage under `gq.redo.<username>` in blipwork and `gq.redo.local`
  in the standalone. One code path (`js/redo.js`, new, synced), no backend change, no
  migration. Per device for now (phone and laptop hold different baskets); a server
  basket is a possible phase 2 and is NOT in this plan.
- Cap 20 entries. Dedupe on `questId:skillId`. Wrong AND skipped items go in (a skip
  is "I did not know"); half-mark items (second try) do NOT.
- Filled at `finish()` of a NORMAL round only: for each `record` entry with outcome
  `wrong` or `skipped`, `redo.add(entry)`. Never filled by a redo round.
- Cleared per entry: a redo item answered `full` or `hinted` removes its entry; `half`,
  `wrong`, `skipped` keep it and bump `misses`. A learner can also drop one entry by
  hand ("Los dit" / "Drop it"). No "clear all" button (one tap should not wipe the list).

**The redo round.** New export in `js/play.js`: `startRedo(entries, onFinish, onQuit,
opts)`.
- Builds one item per entry with a new helper `buildForSkill(questId, skillId)` in
  `js/quests/index.js`: find the skill in `q.skills`, call `s.gen()` (retry up to 5 times
  on null, same guard style as `buildRound`), stamp `skillId` and `concept`. Respect the
  semicircle gate exactly as `buildRound` does (`s.techOnly && !CONTENT.semicircles` →
  drop the entry, never deal it). Exam-mode entries (q7, `buildAll`) are regenerated from
  `buildAll()` filtered on the stored `skillId`; if nothing matches, the entry is dropped
  silently, never an error.
- `S.redo = true`. No intro beats, no boost banner (hints stay available, second chance
  stays as the question itself allows), no comeback bonus, `xp` stays 0, `S.q` is a
  synthetic quest `{ id: "redo", title: B("Try again", "Probeer weer"), rounds: n }`.
  The progress row reads "2 van 5" as usual.
- **No XP, no save.** `startRedo` never calls the backend's `saveResult` and the
  blipwork host never calls `funfunSubmit` for it. The header says so: "Geen XP, net
  oefening" / "No XP, just practice". This is what keeps the server untouched and makes
  the round un-farmable.
- On finish: `onFinish({ questId: "redo", redo: true, score, total, answered: record,
  cleared: [ids], kept: [ids] })`, after `redo.settle(record)` updated the basket.
- The swipe-back ("◀ Vorige", built 2026-09-04) works inside a redo round for free,
  because it is a normal `play.js` round.

**Where the learner meets it.**
1. Results card, after a normal round with misses: one line "Jy het 2 verkeerd gehad.
   Wil jy hulle weer probeer?" / "You got 2 wrong. Want to try them again?" and a
   secondary button "Probeer hulle weer" / "Try them again" that starts a redo round of
   THIS round's misses only (they are already in the basket).
2. A basket chip, visible only when the basket is not empty: standalone on the map
   screen; blipwork on the Functions chapter's 📈 strip. Text "🔁 Probeer weer (3)" /
   "🔁 Try again (3)". Tapping opens the basket sheet.
3. The basket sheet: each entry as a card with the quest title, the original prompt
   text, "×2" when `misses` > 1, and a small "Los dit" link. One primary button "Begin"
   / "Start" runs a redo round over the whole basket (cap the round at 8 items, oldest
   first, so a big basket is not one endless round). A redo results card lists
   "Reggekry: 2 · Bly in die mandjie: 1" / "Got right: 2 · Still in the basket: 1".

**Afrikaans copy rules.** Informal "jy". "Klik op" for taps, "Trek" / "Skuif" for drags
(never "sleep"). No em-dashes anywhere. Strings in `js/i18n.js` via `B("English",
"Afrikaans")`.
